## Deliverable

Architectural decisions for 3 gert-tui interface gaps (§3.5):

1. **EventKindStepOutput** — Real-time step output streaming via event stream
2. **EventKindRunFailed** — Distinguish failure from completion (vs. SUCCESS-only current model)
3. **RunState.Plan** — Expose ExecutionPlan for TUI step list panel population

## Decision Framework

**Option A** (Rejected): Polling + State Machine — Client polls for state changes; engine maintains full state history  
**Option B** (Chosen): Event-Based + Field Addition — Engine emits StepOutput/RunFailed events; RunState carries Plan

### Rationale for Option B

- **Efficiency**: Event-based avoids polling overhead; TUI UI updates on actual changes
- **Simplicity**: No state machine complexity; events are domain facts
- **Alignment**: Matches gert v2 event-stream architecture already in place
- **Extensibility**: New event kinds added incrementally without redesign
- **Backward Compat**: Plan field is additive; existing consumers unaffected

## Implementation Scope

All 3 changes land in the **event.go** and **run.go** packages:

- `pkg/trace/event.go` — EventKindStepOutput, EventKindRunFailed constants
- `pkg/engine/run.go` — RunState.Plan field definition
- `internal/engine/engine.go` — Event emission logic during step/run execution
