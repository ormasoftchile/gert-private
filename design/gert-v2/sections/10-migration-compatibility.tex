\chapter{Migration and Compatibility}

Gert v2 is a breaking redesign from v1. This section specifies the migration path from \texttt{runbook/v0} and \texttt{runbook/v1} to the v2 schema, defines what \texttt{gert migrate} (v2 version) must accomplish, and establishes compatibility guarantees for existing runbooks, tools, providers, and integrations.

Migration is a launch blocker for adoption: every operator with a v1 runbook must understand what breaks, what is automatically migrated, and what requires manual effort. This chapter provides a concrete, actionable roadmap for teams moving from v1 to v2.

\section{v1 → v2 Compatibility Matrix}
\label{sec:compat-matrix}
% ─────────────────────────────────────────────────────────────────────────────

The following table catalogs every v1 feature, interface, and artifact and specifies its v2 status. A BREAKING change requires manual intervention or automated migration; a COMPATIBLE change preserves the v1 contract.

\begin{center}
\small
\begin{tabular}{lllp{5cm}}
\textbf{v1 Feature/Interface} & \textbf{Status} & \textbf{v2 Change} & \textbf{Migration Notes} \\
\hline
\texttt{runbook/v0} schema & BREAKING & Removed & Migrate to v1 first, then v2 \\
\texttt{runbook/v1} schema & BREAKING & Promoted fields & \texttt{gert migrate} auto-rewrites \\
\texttt{provider/v0} schema & BREAKING & New namespace & Manual rewrite required \\
\texttt{tool/v0} schema & BREAKING & New fields & \texttt{gert migrate} rewrites \\
CLI: \texttt{gert run} & COMPATIBLE & New flags added & All v1 flags preserved \\
CLI: \texttt{gert test} & COMPATIBLE & Unchanged & \\
CLI: \texttt{gert serve} & COMPATIBLE & New RPC methods & v1 methods preserved \\
CLI: \texttt{gert validate} & COMPATIBLE & v2 schema aware & \\
CLI: \texttt{gert migrate} & COMPATIBLE & v0→v1→v2 path & New \texttt{--to-v2} flag \\
JSON-RPC: \texttt{exec/*} & COMPATIBLE & Additive & New methods; old methods unchanged \\
JSON-RPC: \texttt{runbook/*} & COMPATIBLE & Additive & \\
JSONL trace format & BREAKING & New envelope & See §10.5 \\
Extension handshake & BREAKING & New capability fields & See §10.4 \\
Event stream schema & BREAKING & New event kinds & Old events preserved \\
VS Code extension protocol & COMPATIBLE & Backward compat & v2 extension reads v1 traces \\
TUI adapter & COMPATIBLE & Event-based & \\
\end{tabular}
\end{center}

\paragraph{Key takeaways:}
\begin{itemize}
  \item All \textbf{CLI commands and flags} are backward compatible. Existing scripts using \texttt{gert run} continue to work.
  \item All \textbf{JSON-RPC methods} are backward compatible. The v2 \texttt{gert serve} daemon accepts v1 client requests.
  \item The \textbf{runbook YAML schema} has breaking changes (field promotions, renames). Automated migration is provided via \texttt{gert migrate}.
  \item The \textbf{tool and provider schemas} have breaking changes. Manual updates required.
  \item The \textbf{JSONL trace format} has breaking changes (new envelope fields). Historical trace readers must be updated.
  \item The \textbf{extension handshake} has breaking changes. Extension authors must adopt the v2 protocol.
\end{itemize}

\section{Schema Migration: Runbook YAML}
\label{sec:runbook-migration}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Breaking Changes Summary}

The v1 → v2 runbook schema migration involves three categories of change:

\begin{enumerate}
  \item \textbf{Field promotions:} Seven \texttt{meta.*} fields are promoted to top-level (§3.2.4).
  \item \textbf{Step type renames:} \texttt{collector} → \texttt{manual}, \texttt{router} → \texttt{end}.
  \item \textbf{New required fields:} \texttt{\$schema}, \texttt{id} (derived from \texttt{name} if absent).
\end{enumerate}

All other runbook semantics are preserved. Step execution behavior, governance primitives, evidence capture, and input/output contracts remain unchanged.

\subsection{Before and After Example}

\textbf{v1 runbook (simple.runbook.yaml):}
\begin{minted}{yaml}
apiVersion: runbook/v1

meta:
  name: service-health-check
  kind: operational
  description: Check service health and restart if needed
  vars:
    service_name: "api-server"
  governance:
    allowed_commands: [systemctl, curl, jq]

flow:
  - step:
      id: check_status
      type: cli
      title: Check service status
      with:
        argv: ["systemctl", "status", "{{ .service_name }}"]
      capture:
        exit_code: exit_status

  - step:
      id: prompt_restart
      type: collector
      title: Service is down. Restart?
      evidence:
        - kind: text
          name: decision

  - step:
      id: restart_service
      type: cli
      when: "{{ eq .decision \"yes\" }}"
      with:
        argv: ["systemctl", "restart", "{{ .service_name }}"]
\end{minted}

\textbf{v2 runbook (migrated):}
\begin{minted}{yaml}
$schema: "https://schemas.gert.dev/runbook/v2.json"
apiVersion: runbook/v2

id: service-health-check
name: Service Health Check
kind: operational
description: Check service health and restart if needed

vars:
  service_name: "api-server"

governance:
  allowed_commands: [systemctl, curl, jq]

flow:
  - step:
      id: check_status
      type: cli
      title: Check service status
      with:
        argv: ["systemctl", "status", "{{ .service_name }}"]
      capture:
        exit_code: exit_status

  - step:
      id: prompt_restart
      type: manual
      title: Service is down. Restart?
      evidence:
        - kind: text
          name: decision

  - step:
      id: restart_service
      type: cli
      when: "{{ eq .decision \"yes\" }}"
      with:
        argv: ["systemctl", "restart", "{{ .service_name }}"]
\end{minted}

\section{Automated Migration Tool}
\label{sec:migrate-tool}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Command Specification}

The \texttt{gert migrate} command automates runbook, tool, and provider migrations. It is extended in v2 to support v1→v2 migration.

\begin{minted}{bash}
# Preview migration (dry-run)
gert migrate --to-v2 --dry-run runbook.yaml

# Migrate a single runbook in-place
gert migrate --to-v2 runbook.yaml

# Migrate all runbooks in a directory tree
gert migrate --to-v2 ./runbooks/

# Output migrated YAML to stdout (for review)
gert migrate --to-v2 --output - runbook.yaml

# Check if migration is needed (exit 1 if needed, 0 if already v2)
gert migrate --to-v2 --check runbook.yaml
\end{minted}

\subsection{Flags}

\begin{center}
\begin{tabular}{llp{7cm}}
\textbf{Flag} & \textbf{Type} & \textbf{Description} \\
\hline
\texttt{--to-v2} & bool & Enable v1→v2 migration mode \\
\texttt{--dry-run} & bool & Preview changes without writing \\
\texttt{--output PATH} & string & Write to file or \texttt{-} for stdout \\
\texttt{--check} & bool & Exit 1 if migration needed, 0 otherwise \\
\texttt{--force} & bool & Overwrite existing v2 files \\
\texttt{--backup} & bool & Create \texttt{.v1.bak} backup before rewrite (default: true) \\
\end{tabular}
\end{center}

\subsection{Migration Algorithm}

The migration tool performs the following transformations in order:

\begin{enumerate}
  \item \textbf{Parse input:} Read YAML with v1 parser. If \texttt{apiVersion} is already \texttt{runbook/v2}, exit 0 (no-op).
  \item \textbf{Version check:} If \texttt{apiVersion} is \texttt{runbook/v0}, emit error: ``v0 must be migrated to v1 first''.
  \item \textbf{Add \texttt{\$schema}:} Insert \texttt{\$schema: "https://schemas.gert.dev/runbook/v2.json"} at document top.
  \item \textbf{Update \texttt{apiVersion}:} Change \texttt{runbook/v1} → \texttt{runbook/v2}.
  \item \textbf{Derive \texttt{id}:} If no \texttt{meta.name}, derive from filename. Convert to kebab-case (e.g., \texttt{service\_health} → \texttt{service-health}).
  \item \textbf{Promote \texttt{meta.*} fields:} Extract \texttt{meta.name}, \texttt{meta.kind}, etc.\ and move to top-level. Capitalize \texttt{name} for human readability.
  \item \textbf{Rename step types:} \texttt{collector} → \texttt{manual}, \texttt{router} → \texttt{end}.
  \item \textbf{Rename \texttt{tree}:} If \texttt{tree:} is present, rename to \texttt{flow:}.
  \item \textbf{Rewrite \texttt{tools}:} Convert shorthand \texttt{tools: [name]} to structured \texttt{toolRefs: [\{name, version?\}]}.
  \item \textbf{Validate:} Parse the migrated YAML with the v2 parser. If validation fails, rollback and report error.
  \item \textbf{Write output:} If \texttt{--output} is specified, write to that path; otherwise rewrite in-place.
\end{enumerate}

\subsection{Diff Report}

The migration tool emits a structured diff report showing all changes:

\begin{verbatim}
Migration report for service-health-check.runbook.yaml:
  [CHANGE] apiVersion: runbook/v1 → runbook/v2
  [ADD]    $schema: "https://schemas.gert.dev/runbook/v2.json"
  [ADD]    id: "service-health-check"
  [MOVE]   meta.name → name
  [MOVE]   meta.kind → kind
  [MOVE]   meta.description → description
  [MOVE]   meta.vars → vars
  [MOVE]   meta.governance → governance
  [RENAME] step "prompt_restart": type collector → manual
  [OK]     3 steps validated successfully

Summary: 8 changes applied. No errors.
\end{verbatim}

\subsection{Error Handling}

If migration fails (e.g., v2 validation error, ambiguous field conflict), the tool:
\begin{enumerate}
  \item Rolls back any partial changes (if in-place mode).
  \item Emits a structured error message with file, line, and remediation advice.
  \item Exits with status 1.
\end{enumerate}

Example error:

\begin{minted}{yaml}
ERROR: Migration failed for service-health-check.runbook.yaml
  Line 14: step "check_status" has invalid v2 field "with.argv"
  Suggestion: v2 uses "with.command" for CLI steps. Update manually.
\end{minted}

\section{Provider and Tool Migration}
\label{sec:provider-tool-migration}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Tool Definitions (\texttt{.tool.yaml})}

The v1 \texttt{tool/v0} schema is replaced by \texttt{tool/v2}. Key changes:

\begin{enumerate}
  \item \textbf{New required field:} \texttt{transport} (one of \texttt{stdio}, \texttt{jsonrpc}, \texttt{mcp}).
  \item \textbf{Renamed field:} \texttt{executable} → \texttt{command} (aligns with runbook YAML).
  \item \textbf{New field:} \texttt{capabilities} (list of required capability grants; see §4).
\end{enumerate}

\textbf{v1 tool definition:}
\begin{minted}{yaml}
apiVersion: tool/v0
name: kubectl
executable: /usr/local/bin/kubectl
args_template: "{{ .args }}"
\end{minted}

\textbf{v2 tool definition:}
\begin{minted}{yaml}
$schema: "https://schemas.gert.dev/tool/v2.json"
apiVersion: tool/v2

id: kubectl
name: kubectl
transport: stdio
command: /usr/local/bin/kubectl
args_template: "{{ .args }}"
capabilities:
  - exec:command
  - net:egress
\end{minted}

\paragraph{Migration tool support.} The \texttt{gert migrate --to-v2} command rewrites tool definitions automatically, but \textbf{requires manual review} for the \texttt{capabilities} field (the tool cannot infer required capabilities statically).

\subsection{Provider Definitions (\texttt{.provider.yaml})}

The v1 \texttt{provider/v0} schema is replaced by \texttt{provider/v2}. Key changes:

\begin{enumerate}
  \item \textbf{Namespace convention:} Provider fields now use a \texttt{provider/*} namespace to avoid name collisions with core schema fields.
  \item \textbf{New resolution protocol:} v2 providers declare a \texttt{resolve\_method} (one of \texttt{static}, \texttt{env}, \texttt{prompt}, \texttt{jsonrpc}).
\end{enumerate}

\textbf{v1 provider definition:}
\begin{minted}{yaml}
apiVersion: provider/v0
name: incident-id
source: env
env_var: INCIDENT_ID
\end{minted}

\textbf{v2 provider definition:}
\begin{minted}{yaml}
$schema: "https://schemas.gert.dev/provider/v2.json"
apiVersion: provider/v2

id: incident-id
name: Incident ID
resolve_method: env
provider/env:
  var_name: INCIDENT_ID
  required: true
\end{minted}

\paragraph{Migration tool support.} The \texttt{gert migrate --to-v2} command partially rewrites provider definitions but \textbf{requires manual namespace updates} for custom provider fields.

\section{Extension Migration}
\label{sec:extension-migration}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Handshake Protocol Changes}

The v2 extension handshake introduces new capability negotiation (§4.3). Extensions must update their initialization sequence to:

\begin{enumerate}
  \item Declare supported \texttt{protocol\_version} (set to \texttt{"2.0"}).
  \item Declare required \texttt{capabilities} (list of capability names).
  \item Handle \texttt{CapabilityDenied} responses gracefully.
\end{enumerate}

\textbf{v1 handshake (JSON-RPC):}
\begin{verbatim}
→ {"jsonrpc":"2.0","method":"initialize","params":{"version":"1.0"}}
← {"jsonrpc":"2.0","result":{"ready":true}}
\end{verbatim}

\textbf{v2 handshake (JSON-RPC):}
\begin{verbatim}
→ {"jsonrpc":"2.0","method":"initialize","params":{
    "protocol_version":"2.0",
    "capabilities":["fs:read","net:egress"]
  }}
← {"jsonrpc":"2.0","result":{
    "granted_capabilities":["fs:read"],
    "denied_capabilities":["net:egress"]
  }}
\end{verbatim}

\subsection{Extension Compatibility Shim}

To ease the transition, the v2 Extension Host provides a \textbf{v1 compatibility shim}:

\begin{itemize}
  \item Extensions that declare \texttt{protocol\_version: "1.0"} are accepted.
  \item The shim grants all capabilities by default (insecure, but backward-compatible).
  \item A deprecation warning is logged: ``Extension 'foo' uses deprecated v1 protocol. Update to v2 by YYYY-MM-DD.''
  \item The shim will be removed in v2.1 (approximately 6 months after v2.0 release).
\end{itemize}

\subsection{Extension Author Checklist}

Extension authors must:
\begin{enumerate}
  \item Update \texttt{protocol\_version} to \texttt{"2.0"} in the \texttt{initialize} method.
  \item Declare all required capabilities in the handshake.
  \item Test against the v2 Extension Host in capability-denied scenarios.
  \item Update extension manifest to declare minimum gert version (\texttt{min\_gert\_version: "2.0.0"}).
  \item Review the capability taxonomy (§4.4) and minimize requested capabilities.
\end{enumerate}

\section{Trace Format Migration}
\label{sec:trace-migration}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Breaking Changes in JSONL Trace}

The v2 trace format (§12.1) adds mandatory envelope fields. The v1 trace format had:

\begin{verbatim}
{"seq":1,"type":"run/started","timestamp":"...","data":{...}}
\end{verbatim}

The v2 trace format requires:

\begin{verbatim}
{"event_id":"...","run_id":"...","runbook_id":"...","timestamp":"...",
 "kind":"run/started","sequence":1,"payload":{...}}
\end{verbatim}

\paragraph{Field mapping:}
\begin{center}
\begin{tabular}{lll}
\textbf{v1 Field} & \textbf{v2 Field} & \textbf{Notes} \\
\hline
\texttt{seq} & \texttt{sequence} & Renamed \\
\texttt{type} & \texttt{kind} & Renamed \\
\texttt{data} & \texttt{payload} & Renamed \\
(none) & \texttt{event\_id} & New (UUID v4) \\
(none) & \texttt{run\_id} & New (extracted from file path in v1) \\
(none) & \texttt{runbook\_id} & New (from \texttt{meta.name}) \\
\end{tabular}
\end{center}

\subsection{Trace Replay Compatibility}

The v2 \texttt{gert replay} command can read v1 traces \textbf{in compatibility mode}:

\begin{enumerate}
  \item Detect v1 format by presence of \texttt{type} field (v2 uses \texttt{kind}).
  \item Synthesize missing fields: \texttt{event\_id} (new UUID), \texttt{run\_id} (from file path), \texttt{runbook\_id} (from first event payload).
  \item Map \texttt{seq} → \texttt{sequence}, \texttt{type} → \texttt{kind}, \texttt{data} → \texttt{payload}.
  \item Replay as normal.
\end{enumerate}

Compatibility mode will be removed in v2.1.

\subsection{Trace Archive Migration Tool}

Teams with historical v1 trace archives can migrate them to v2 format using:

\begin{minted}{bash}
gert trace migrate --to-v2 .runbook/runs/*/trace.jsonl
\end{minted}

This rewrites all trace files in-place, adding the required v2 envelope fields.

\section{Rollout Strategy}
\label{sec:rollout-strategy}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Recommended Adoption Path}

Teams should adopt v2 in four phases:

\paragraph{Phase 1: Read-Only Validation (Week 1-2)}
\begin{enumerate}
  \item Install gert v2.0 alongside v1 (both can coexist).
  \item Run \texttt{gert validate --v2} against existing v1 runbooks.
  \item Run \texttt{gert migrate --to-v2 --dry-run --check} to identify migration scope.
  \item Review migration reports; identify runbooks that require manual fixups.
\end{enumerate}

\paragraph{Phase 2: Schema Migration (Week 3-4)}
\begin{enumerate}
  \item Migrate runbooks in a staging directory: \texttt{gert migrate --to-v2 ./runbooks/}.
  \item Review migrated YAML for correctness (especially governance blocks, tool refs).
  \item Run \texttt{gert validate} against migrated runbooks to confirm v2 compliance.
  \item Commit migrated runbooks to version control (with \texttt{.v1.bak} backups retained).
\end{enumerate}

\paragraph{Phase 3: Extension and Tool Migration (Week 5-6)}
\begin{enumerate}
  \item Update all \texttt{.tool.yaml} files: add \texttt{transport} and \texttt{capabilities} fields.
  \item Update all \texttt{.provider.yaml} files: namespace custom fields.
  \item Update custom extensions: implement v2 handshake, declare capabilities.
  \item Test extensions in v2 runtime with governance policies enabled.
\end{enumerate}

\paragraph{Phase 4: Integration Migration (Week 7-8)}
\begin{enumerate}
  \item Update integrations (CI/CD pipelines, monitoring scripts) to use v2 CLI flags.
  \item Update JSON-RPC clients (if any) to handle new event kinds (§6).
  \item Update trace parsers to handle v2 envelope format (§12).
  \item Decommission v1 runtime once all integrations are v2-native.
\end{enumerate}

\subsection{Parallel Operation}

During the migration period, v1 and v2 runtimes can coexist:

\begin{itemize}
  \item Install v2 as \texttt{/usr/local/bin/gert2} or via version manager (\texttt{gert@2}).
  \item Run v1 runbooks with \texttt{gert run} (v1 binary).
  \item Run v2 runbooks with \texttt{gert2 run} or \texttt{gert --version 2 run}.
  \item The v2 runtime rejects v0 runbooks; v1 runbooks are accepted in compatibility mode.
\end{itemize}

\section{v1 Compatibility Shim}
\label{sec:v1-shim}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Decision: Provide a v1 Compatibility Shim for 6 Months}

The v2 parser and runtime include a \textbf{v1 compatibility mode} that accepts \texttt{runbook/v1} documents and silently normalizes them to v2 semantics. This shim is enabled by default in v2.0 and will be removed in v2.1 (approximately 6 months after v2.0 release).

\paragraph{Rationale:}
\begin{itemize}
  \item Lowers the migration barrier for large organizations with hundreds of runbooks.
  \item Allows operators to adopt v2 runtime immediately without waiting for schema migration.
  \item Provides a grace period for extension authors to update their code.
  \item Encourages migration by emitting deprecation warnings (\texttt{--strict} mode treats warnings as errors).
\end{itemize}

\subsection{Shim Behavior}

The compatibility shim:
\begin{enumerate}
  \item Accepts \texttt{apiVersion: runbook/v1} documents.
  \item Silently applies the same transformations as \texttt{gert migrate --to-v2}.
  \item Emits deprecation warnings to stderr:
  \begin{verbatim}
  WARN: runbook 'service-health-check' uses deprecated runbook/v1 schema.
        Run 'gert migrate --to-v2 runbook.yaml' to upgrade.
        v1 support will be removed in gert v2.1 (2026-10-18).
  \end{verbatim}
  \item If \texttt{--strict} flag is passed, treats deprecation warnings as errors (exit 1).
\end{enumerate}

\subsection{Shim Removal}

The v1 compatibility shim will be removed in v2.1 (target: 6 months post-v2.0 release). After removal:
\begin{itemize}
  \item The v2 parser rejects \texttt{runbook/v1} documents with error: ``v1 schema not supported. Migrate to v2.''
  \item All v1 runbooks must be migrated using \texttt{gert migrate --to-v2}.
  \item The v1 compatibility shim code is deleted from the codebase.
\end{itemize}

\section{Open Questions and Risks}
% ─────────────────────────────────────────────────────────────────────────────

\subsection{Open Questions}

\begin{enumerate}
  \item \textbf{Provider field namespacing:} Should v2 enforce a strict \texttt{provider/*} namespace, or allow custom prefixes? (Recommendation: strict namespace, relaxed in v2.1 if needed.)
  \item \textbf{Migration of tool discovery paths:} v1 searches \texttt{tools/} by default. Should v2 preserve this, or require explicit \texttt{--tool-dir} flags? (Recommendation: preserve default path for compatibility.)
  \item \textbf{Trace archive retention:} Should \texttt{gert trace migrate} preserve v1 traces as \texttt{.v1.jsonl} backups? (Recommendation: yes, with \texttt{--no-backup} opt-out.)
\end{enumerate}

\subsection{Migration Risks}

\begin{enumerate}
  \item \textbf{Runbooks with custom \texttt{meta.*} fields:} If a v1 runbook has custom fields under \texttt{meta.*}, migration may fail. Mitigation: emit detailed error messages with field paths.
  \item \textbf{Extensions relying on v1-specific behaviors:} Some extensions may depend on v1 event ordering or field names. Mitigation: provide comprehensive v2 migration guide for extension authors.
  \item \textbf{Historical trace parsing:} Teams with custom trace analysis scripts will need updates. Mitigation: publish a trace format migration guide with field mappings.
\end{enumerate}

\section{Summary}
% ─────────────────────────────────────────────────────────────────────────────

Gert v2 introduces breaking changes to the runbook, tool, and provider schemas, the JSONL trace format, and the extension handshake protocol. All changes are necessary to support the new capability-based security model (§7), the event-driven architecture (§6), and the governance primitives (§11).

The migration path is designed to minimize disruption:
\begin{itemize}
  \item \textbf{CLI and JSON-RPC contracts are backward-compatible.}
  \item \textbf{Schema migration is automated} via \texttt{gert migrate --to-v2}.
  \item \textbf{v1 compatibility shim} provides a 6-month grace period for runbook and extension migration.
  \item \textbf{Phased rollout} allows teams to adopt v2 incrementally over 8 weeks.
\end{itemize}

Teams should begin migration planning with Phase 1 (read-only validation) and proceed through schema, extension, and integration migration in sequence. The v1 runtime will reach end-of-life 12 months after v2.0 release, giving organizations ample time to transition.
