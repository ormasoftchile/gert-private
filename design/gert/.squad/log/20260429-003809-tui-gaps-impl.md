## Summary

Closed 3 critical interface gaps blocking gert-tui step-list and output panels:

### Gap 1: EventKindStepOutput

**Problem**: TUI cannot stream real-time step output; engine only emitted completion events  
**Solution**: Added `EventKindStepOutput` event kind emitted incrementally as step captures stdout/stderr  
**Impact**: TUI output panel can now display live execution progress

### Gap 2: EventKindRunFailed

**Problem**: Engine model conflates "complete" with "succeeded"; no distinction for failure  
**Solution**: Added `EventKindRunFailed` event emitted when run terminates with error  
**Impact**: TUI can show failed runs visually distinct from successful ones; enables retry/abort logic

### Gap 3: RunState.Plan

**Problem**: TUI step-list panel cannot populate; no access to ExecutionPlan structure  
**Solution**: Added `RunState.Plan *ExecutionPlan` field populated at run initialization  
**Impact**: TUI can render step names, descriptions, order without parsing raw YAML

## Architecture Decision

Chose **event-based + field addition** (Option B) over polling-based state machine (Option A):
- Efficient: No polling overhead
- Simple: Events are domain facts, no complex state tracking
- Aligned: Matches gert v2 event-stream design
- Extensible: New event kinds added incrementally
