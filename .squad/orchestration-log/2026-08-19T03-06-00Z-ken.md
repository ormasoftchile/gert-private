## Key Design Insights

### Vacuity Problem — Fourth Occurrence

The original redaction tests (QBLD-1/2/3) targeted `buildRunChatQuery()`, whose signature cannot receive raw input values. Every assertion was vacuous — a mutation that leaks secrets at the production call site passed all tests unchanged.

**Root cause:** Testing a helper function that is structurally incapable of receiving the sensitive data, then claiming redaction is proven.

**Remedy:** Extract call-site logic into a vscode-free DI module and inject REAL collaborators in tests. HANDOFF-4 proves the inputs actually reached the store.

### Mutation Control Discipline

Mutation #1 (Cristiano's): Append `collectedInputs` to query at production call site → HANDOFF-3 fails.  
Mutation #2: Pass `{}` instead of real inputs to store → HANDOFF-4 fails.

Both mutations are detected only because REAL collaborators were injected, making the data flow observable.

### Empirically Unverified Claims

1. `vscode.lm.invokeTool()` acceptance of cached token for deferred invocations
2. Awaited continuation inside a chat handler holding the context alive
3. `workbench.action.chat.open` with `isPartialQuery: false` auto-submission

These remain unverified in a live VS Code session. The failure modes are named and observable; the architecture is sound but the empirics awaits deployment.
