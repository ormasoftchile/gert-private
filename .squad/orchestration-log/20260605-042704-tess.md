### Conflict 2: `str.foo` expression — GXL-PARSE-006 or GXL-PARSE-010?

**Vector:** TV-GXL-PARSE-083  
**Input:** `str.foo` (no parentheses, where `foo` is not a known str method)

**Parse flow:** PEG ordered alternation tries NamespaceCall before GDP. Fails at NamespaceCall (no LPAREN), falls through to GDP, fails because `str` is KW_STR (keyword), then falls through to parse error.

**Ambiguity:** Error should be:
- GXL-PARSE-006 (unknown method — attempted as NamespaceCall)?
- GXL-PARSE-010 (keyword as identifier — attempted as GDP)?
- GXL-PARSE-001 (unexpected token — falls through all alternatives)?

**Current:** Vector marked GXL-PARSE-010 with note flagging ambiguity.

**Action Required:** Barbara arbitrates and patches grammar.

**Vector:** TV-GXL-PARSE-061  
**Input:** `1.2.3`

**Tokenization:** Lexer would parse as NUMBER(`1.2`) + DOT + NUMBER(`3`).

**Parse error:** GXL-PARSE-001 (unexpected DOT after Primary) rather than GXL-PARSE-003 (malformed numeric token).

**Current:** Vector assigns GXL-PARSE-001 with note.

**Action Required:** Barbara clarifies whether `1.2.3` is a lexer error (GXL-PARSE-003) or parse error (GXL-PARSE-001), and whether "malformed numeric token" includes multi-dot sequences.

### Ambiguity 2: String concatenation as GXL-PARSE-007

**Reference:** gxl.ebnf §2.6 lists "string concatenation" as forbidden with error GXL-PARSE-007.

**Problem:** `"a" + "b"` is syntactically indistinguishable from numeric addition at parse time — parser lacks type information about literals. Error cannot be detected at parse time; must be raised at evaluation as GXL-TYPE-003.

**Resolution:** No vector written for this case in TV-GXL-PARSE; deferred to TV-GXL-EVAL with GXL-TYPE-003.

**Action Required:** Barbara confirms whether GXL-PARSE-007 description should be amended to remove "string concatenation" (not parse-time detectable), or whether parser should special-case literal-to-literal `+` as forbidden.

### Ambiguity 3: Zero-arg `len()`

**Reference:** gxl.ebnf §6 OI-GXL-06

**Structure:** LenCall = KW_LEN LPAREN Expression RPAREN requires Expression, so `len()` fails with unexpected RPAREN where Expression expected.

**Error:** GXL-PARSE-001 (unexpected RPAREN), NOT GXL-TYPE-004.

**Conclusion:** No missing error code; parse behavior is correct. TV-GXL-EVAL will cover zero-arg namespace calls triggering GXL-TYPE-004.
